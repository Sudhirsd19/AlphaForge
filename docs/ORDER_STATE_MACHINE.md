# AlphaForge — Order State Machine & Emergency Protection Specification

---

## 1. Purpose & Philosophy

The **AlphaForge Order State Machine (Phase 7)** (`alphaforge.execution`) establishes deterministic, fail-closed order lifecycle governance and the Emergency Unprotected Position Protocol.

It guarantees:
- Every order follows an explicit, guarded finite state machine (FSM).
- Illegal or out-of-order transitions are strictly rejected without mutating order state.
- Terminal states are permanent and cannot be silently resurrected.
- A filled position without resting stop-loss protection is treated as a P0 Emergency, triggering an immediate liquidation command.

---

## 2. Phase 7 Scope & Boundaries

### Included in Phase 7:
1. Formal 17-state order lifecycle state machine (`alphaforge.execution.state_machine`).

3. Thread-safe atomic mutations via `threading.RLock`.
4. Immutable transition events and audit trail (`TransitionEvent`).
5. Emergency Unprotected Position Protocol and synchronous watchdog (`ProtectionWatchdog`).
6. Broker-independent emergency exit command (`EmergencyExitCommand`).

- **NO real order routing or network sockets** (WebSockets, REST endpoints).
- **NO live credentials, API keys, or broker secrets**.
- **NO crash recovery or persistent database ledger** (deferred to Phase 8).
- **NO backtest, replay, or failure-injection engines** (deferred to Phase 10–12).
- **`LIVE_TRADING = FALSE`** strictly preserved.

## 3. Authoritative States

The state machine implements the exact closed vocabulary from the Master Specification:

1. `CREATED`: Initial order intent generated by strategy; pre-submission validation incomplete.
2. `VALIDATED`: Approved by Risk Engine against all risk and account invariants.
3. `REJECTED`: Rejected during pre-trade risk validation or broker pre-submission checks.
4. `SUBMITTED`: Dispatched to execution boundary; awaiting receipt confirmation.
5. `ACKNOWLEDGED`: Broker receipt confirmed and order placed on venue order book.
6. `PARTIALLY_FILLED`: Execution reported for a fraction of total intended quantity.
7. `FILLED`: 100% of intended entry quantity executed.
8. `PROTECTION_PENDING`: Stop-loss protection order dispatched; awaiting broker confirmation.
9. `PROTECTED`: Resting stop-loss order confirmed on exchange order book.
10. `EXIT_PENDING`: Exit order (target or stop) submitted to market.
11. `PARTIAL_EXIT`: Exit execution partially filled; position reduced but not flat.
12. `CLOSED`: Position completely flat; P&L realized.
13. `CANCELLED`: Order cancelled without any fill (or remaining unfilled balance cancelled).
14. `UNKNOWN`: Communication lost or network dropped during transit.
15. `RECONCILING`: State actively being queried and reconciled against venue facts.
16. `MANUAL_ESCALATION`: Automatic safe resolution impossible; human intervention mandated.

---

## 4. Full Legal Transition Matrix

Transitions are strictly validated against `ALLOWED_TRANSITIONS`:

```text
CREATED             --> VALIDATED, REJECTED
VALIDATED           --> SUBMITTED, CANCELLED
SUBMITTED           --> ACKNOWLEDGED, UNKNOWN, REJECTED
ACKNOWLEDGED        --> PARTIALLY_FILLED, FILLED, UNKNOWN, CANCELLED
PARTIALLY_FILLED    --> FILLED, UNKNOWN, CANCELLED
FILLED              --> PROTECTION_PENDING
PROTECTION_PENDING  --> PROTECTED, MANUAL_ESCALATION
PROTECTED           --> EXIT_PENDING
EXIT_PENDING        --> CLOSED, PARTIAL_EXIT, UNKNOWN
PARTIAL_EXIT        --> EXIT_PENDING, CLOSED, UNKNOWN
UNKNOWN             --> RECONCILING
RECONCILING         --> ACKNOWLEDGED, FILLED, CANCELLED, CLOSED, MANUAL_ESCALATION

TERMINAL STATES:
REJECTED            --> (None)
CLOSED              --> (None)
CANCELLED           --> (None)
MANUAL_ESCALATION   --> (None)
```

Any attempt to execute an undeclared transition fails closed with `IllegalStateTransitionError`.

## 5. Transition Validation Rules & Atomicity

State mutations follow an 8-step atomic sequence:
1. Acquire instance re-entrant lock (`RLock`).
2. Check for duplicate/idempotent request (`target_state == current_state` $\rightarrow$ `ALREADY_IN_TARGET_STATE`).
3. Verify `current_state` is not in `TERMINAL_STATES` ($\rightarrow$ `TERMINAL_STATE`).
4. Verify `target_state in ALLOWED_TRANSITIONS[current_state]` ($\rightarrow$ `INVALID_TRANSITION`).
5. Validate preconditions (quantity adjustments, protection flags, filled timestamps).
6. Create immutable `TransitionEvent` audit record.
7. Atomically update `_current_state`, `_updated_at`, and append event to `_history`.
8. Return immutable `TransitionResult(success=True)`.

**Atomicity Guarantee:** A valid transition results in **exactly one** state change and event. An invalid transition results in **zero** state changes, **zero** event additions, and leaves state completely unchanged.

---

## 6. Concurrency & Race Safety

- All mutations and state reads are protected by `threading.RLock`.
- Prevents race conditions such as:
  - Dual simultaneous ACK events.
  - Fill event racing against Cancel request.
  - Watchdog evaluation racing against Protection Confirmation.
- Deduplication logic ensures duplicate events or transitions produce safe `NO-OP` responses without double-mutating order state.

## 7. Protection Lifecycle & Watchdog

```
[ POSITION FILLED ]
        |
        v
[ PROTECTION_PENDING ] ---> Timeout (> 5.0s) or Failure?
        |                                       |
        | (Explicit Confirmation)               | (Timeout / Hazard)
        v                                       v
[ STATE = PROTECTED ]            [ TRIGGER EMERGENCY PROTOCOL ]
                                                |
                                                +---> Halt new entries
                                                +---> Generate EmergencyExitCommand
                                                +---> MANUAL_ESCALATION if unresolvable
```

- **Core Rule:** `FILLED` without confirmed stop-loss is an **EMERGENCY UNPROTECTED POSITION**.
- `PROTECTION_PENDING` represents an in-flight protection request. It is **NOT** confirmed protection.
- The `ProtectionWatchdog` evaluates order state synchronously:
  - If `PROTECTED` and `is_protection_confirmed == True`: `SAFE`.
  - If `PROTECTION_PENDING` within timeout window ($T \le 5.0$s): `UNPROTECTED_HAZARD` (alert, block entries).
  - If `PROTECTION_PENDING` exceeds timeout ($T > 5.0$s): `TIMEOUT_BREACH` (generates emergency liquidation command).
  - If `UNKNOWN`, `RECONCILING`, or metadata mismatch: `ESCALATED`.

---

## 8. Emergency Exit Command

When an unprotected position hazard is confirmed, the watchdog generates an immutable `EmergencyExitCommand`:
- **Directional Safety:**
  - `LONG` position $\rightarrow$ `side = OrderSide.SELL`
  - `SHORT` position $\rightarrow$ `side = OrderSide.BUY`
- **Quantity Safety:**
  - Must equal exact open position quantity ($> 0$).
  - Zero quantity, missing quantity, or guessed quantity is strictly prohibited and escalates to `MANUAL_ESCALATION`.
- **Broker Independence:**
  - Contains no network, WebSocket, or API calls; represents pure structured intent for the downstream execution adapter.

---

## 9. UNKNOWN & Reconciliation Governance

- `UNKNOWN` is a deliberate, fail-closed safety state when communication is lost.
- `UNKNOWN` cannot transition directly to `FILLED`, `PROTECTED`, or `CLOSED`.
- It must enter `RECONCILING`:
  - If venue facts prove resting: `ACKNOWLEDGED`.
  - If venue facts prove execution: `FILLED`.
  - If venue facts prove non-existence: `CANCELLED`.
  - If position was closed: `CLOSED`.
  - If ambiguity persists: `MANUAL_ESCALATION`.
